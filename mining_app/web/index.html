Define what the events mean

A case is a sequence of events analysed together. First choose whose events belong together, then choose whether to split their timeline into days or sessions. Different participants should normally stay separate.

Participant/group columns (required)

Select the participant ID (for example user_id), then use the splitting option below to create days or sessions. If your data already has numbered sessions, select both the participant ID and session ID, and choose One sequence to keep each existing session as a separate case.

For example, no recorded activity between 22:00 and 06:00 could indicate sleep; the morning activity would start a new behavioural day. The algorithm looks for the longest qualifying break of at least 4 hours, favouring breaks that end in the morning. This is an estimate, not measured sleep.

Help: participants, days and sessions

With user_id selected, user 101 and user 102 always have separate timelines. Calendar days splits each person's timeline at the chosen hour: user 101 on May 28 is one case, user 102 on May 28 is a different case. Inactivity sessions splits whenever the gap exceeds your threshold. Behavioural days estimates sleep from long inactivity breaks instead of using a fixed daily boundary.

Behavioural-day rules: the original algorithm considers gaps of at least 4 hours, prioritising gaps ending between 04:00 and noon; otherwise it uses nighttime (20:00-04:00, including 04:00 within a gap) and late-sleep (03:00-10:00) fallbacks. It selects the longest candidate per date, not simply any gap after 21:00. Without a qualifying boundary, all events remain in one sequence. An event spanning the night (such as Screen off) is not itself an inactivity gap.

If sessions are already numbered in your data, select user_id + session_id and choose One sequence. For example, participant 101's sessions 1 and 2 become two separate cases; participant 102's session 1 is another case. No additional splitting is needed. Without existing session numbers, select only user_id and let the day or inactivity method create the cases.

Selecting age + gender alone would pool everybody sharing those values into one timeline; that is usually not a valid individual event sequence. Retain those columns as attributes to filter the population instead.

Times must use ISO date/time. Naive times retain the source clock; timezone-aware times are converted to UTC. Mixed conventions are rejected. Both day methods use that clock: standardise timestamps to your study's intended clock before preparation.

Keep only the attributes your study needs

Unselected columns are removed. Case attributes must be constant in a case, including missingness. Changing measurements belong at event scope; their cohort filters explicitly match any or all events.

Population filters

Filters select whole cases, not individual rule rows. Different filters combine with AND. An event-scope match keeps all events of the matching case. Empty filters mean the full prepared population.

Choose a file name, not a folder path. When mining both levels, downloads use your name with _activity.csv and _category.csv suffixes.

Advanced engine settings

Exported support = cases without a violation / cases. DisCoveR confidence is fulfilled activated traces / activated traces; Declare4Py confidence is fulfilled event activations / event activations. Engine discovery thresholds are not interchangeable with exported support. Zero DisCoveR thresholds discover all rules and may be expensive for large activity vocabularies. Declare4Py requires positive itemset support; its default here is 0.1.
